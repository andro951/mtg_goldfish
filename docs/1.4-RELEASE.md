# Astra 1.4 — expanded card pool and targeting

## Supported pool

Both complete lists supplied for this update are included as selectable deck-editor presets. The union is 310 unique candidate names, including the outside-the-game sections. The local database contains 340 card/token/derived definitions and 343 card/face images, plus the Magic card back. The first list preserves its two physical Arcbound Ravagers; no duplicate was silently deleted.

| Supplied list | Main | Commander | Outside | Active library | Reserve |
| --- | ---: | ---: | ---: | ---: | ---: |
| List 1, expanded | 203 | 1 | 88 | 99 | 104 |
| List 2, refined | 126 | 1 | 41 | 99 | 27 |

Use **Menu → Deck editor → Load one of your supplied lists**, choose a list, then **New test**. Loading a preset replaces the editor only, not the game already in progress. The original legacy candidate pool remains available through Restore supplied pool.

All 150 added candidates have focused mechanic assertions in `tests/expanded-*.test.js`, in addition to legal-entry and registered-ability coverage. Acceptance status is promoted only from explicitly implemented modules through an explicit name allowlist. `tools/verify-card-support.mjs` checks every requested name and the named tests, preserves quantities, constructs each active/reserve split, and writes `test-results/card-support.json`. Release packaging requires that report and the complete passing test results.

The expansion implements the relevant suspend, dredge, offering, improvise, escape, warp, cascade/discover, station, transformation, linked recursion, mana restrictions, landfall, triggered and static effects. Cards with no mana cost expose Suspend rather than pretending an ordinary cast is legal. These are capabilities in the documented goldfish scope, not a claim to implement all of Magic's multiplayer interactions or prove every possible card combination.

## Read-only resources by default

Mana, life, energy, poison and opponent totals are still visible and update through legal card actions. Their plus/minus and clear buttons are hidden unless **Menu → Settings → Manual resource controls** is enabled. The setting is saved, separate from developer overrides. Legal mana sources remain usable during a pending payment.

The new **Deal unblocked damage** phase-bar action calculates the goldfish combat damage step from declared attackers, including implemented first strike, double strike, lifelink and vigilance behavior. Opponents remain abstract and have no blocker AI. Opponent payment/choice prompts are explicitly answered by the player rather than guessed by an AI.

## Target arrows

Declared targets are connected to their stack source using a pointer-transparent SVG overlay. At rest the arrows are mostly transparent; hovering, focusing or selecting the matching stack image emphasizes them. Clicking the selected stack image again dismisses its inspection. Colors distinguish spells from effects. The overlay hides behind application menus and follows moving cards, camera zoom/pan and movable stack windows.

A dashed endpoint at a zone icon represents a target in a closed or offscreen zone; opening that zone switches to the actual card. Costs and non-targeting selections do not produce arrows. Target references include object incarnation, so a card that leaves and returns is not incorrectly treated as the original target.

Geometry reads are batched before SVG writes, updates are coalesced to animation frames, and unchanged geometry is not rebuilt. This avoids adding a separate continuous rendering loop to an otherwise idle table.

## Mana allocation

The suggested payment reserves explicit colored/colorless symbols first. For numeric generic costs it uses available real colorless mana first, then the largest remaining eligible colored pool, proceeding to the next largest if necessary. Restricted mana contributes only when its restriction permits this action. Explicit `{C}` still cannot be paid with colored mana, even when another effect permits spending mana as any color.

This allocates only the existing pool. It never taps a land automatically. Editing the payment remains possible, and cancellation leaves the pending cast/activation uncommitted.

## Browser versus a C# rewrite

The observed interaction bottlenecks were avoidable work in the implementation: rebuilding image-heavy DOM after each selection, repeated geometry/layout reads, recreating drag previews, and doing unnecessary serialization during pointer work. The 1.3 changes reduced those operations; this release retains them and batches target-overlay work as well. Changing language would not by itself fix equivalent redundant work in a new UI.

The delivery therefore remains a portable offline browser application. Profile a reproducible slow game before changing architecture. Expensive rules computations could later move away from the UI thread without throwing away the rules engine, history format and existing tests. No claim is made that every possible long-running board state has identical performance.

## Verification and delivery

The final archive includes editable source, pinned local assets, both supplied deck lists, the test suites and their reports. Release gates require all engine tests, full HTTP/direct-file Chromium tests, isolated single-file offline tests, no skipped checks, exact image hashes, reproducible HTML builds, and a source ZIP that is read back against its per-entry SHA-256 manifest.

`--memory` browser tests are for local authored-HTML inspection where URL navigation is unavailable. Their skipped persistence/download checks are explicit and cannot satisfy release packaging. See `test-results/release.json` in the finished build for actual counts, rather than treating the existence of a test file as proof it ran.


## 1.4.2 interface follow-up

The visual deck builder and the original text workflow are now two separate dialogs sharing one deck source. Side-zone grids choose their row/column shape from the real surface dimensions and are refitted on dock/window resize; detached cards remain detached. Browser acceptance captures narrow, medium, and wide graveyard screenshots and requires substantial occupancy in both axes at every tested size.
